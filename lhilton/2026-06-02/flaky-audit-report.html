Why this matters

Flaky tests are a tax on every engineer, every day

A “flaky” test fails for reasons that have nothing to do with the code being shipped — a clock, a shared cache, test ordering. When CI goes red for no real reason, three expensive things happen:

⏳

Wasted time

Engineers stop and investigate a red build, find nothing wrong, click “re-run,” and wait. We measured 7 commits that did exactly this — failed, then passed green with no code change.

🚨

Eroded trust

When red doesn't reliably mean “broken,” people start ignoring red. That's when a genuinely broken build slips through — the failure mode flaky tests are most dangerous for.

🐢

Slower shipping

Every phantom failure adds a re-run cycle (~15–25 min) before a PR can merge. Concentrated in our fast-moving voice-AI work, it directly slows the teams shipping the most.

The finding

Most red builds are real. A stubborn third are phantoms.

We read the failing logs of all 226 builds, reduced 855 individual test failures to 80 distinct error “fingerprints,” and classified each — then ran an adversarial second pass that argued the opposite verdict before anything was accepted.

The smoking gun: 7 commits failed, then passed — with zero code changes

The same commit went red on one run and green on a re-run. That is the near-irrefutable signature of flakiness. 3 trace directly to flaky tests (all in voice-AI / Communications); the other 4 were lint or “branch out of date” process noise — correctly kept out of the flaky-test set.

Root causes

The 27 phantoms collapse into a handful of mechanisms

Most are shared state leaking between tests running in parallel — one test's leftover cache, clock, or database row poisons the next. The rest are unfrozen clocks, unordered “pick the first row” lookups, and random test data colliding.

Recommendation

Five patterns retire the entire flaky set

These are small, well-understood test-hygiene fixes — not architecture changes. We recommend a focused sprint task on the voice-AI suite first, where the pain is concentrated.

1

Freeze the clock

Tests validating business-hours / callback windows use the live wall clock, so they fail on weekends, holidays, and window edges. Pin Carbon + CarbonImmutable::setTestNow() to a fixed mid-week instant.

Retires ~6 patterns · incl. our #1 flaky test
2

Reset shared state per test

Parallel workers leak cache, container singletons, and in-flight call state. Add Cache::flush() + facade re-binding in beforeEach so one test can't poison the next.

Retires ~15 patterns · the largest bucket
3

Deterministic “first row” lookups

Bare ->first() / latest() on rows sharing a timestamp returns an arbitrary one. Add a stable tiebreaker (->orderByDesc('id')) — a real correctness habit, not just a test fix.

Retires ~3 patterns
4

Unique, deterministic test data

Random ZIPs / indexes collide against DB unique constraints across parallel tax & document tests. Use per-entity sequences instead of fake()->unique()->random.

Retires ~2 patterns · pattern already proven by #6950
5

Give CI workers headroom

A handful of failures are worker crashes (segfault / out-of-memory) with no test assertion at all. Raise worker memory limit / reset per-worker execution timers; add OOM detection.

Retires ~4 patterns · infrastructure
★

Stop hard-coding AI prompt copy in assertions

Many voice-AI tests assert exact prompt wording, which churns daily. These read as flaky and broken. Assert on structure/membership, not literal strings.

Methodology & honesty notes

What was done, and where the limits are

Approach

A single multi-agent workflow ran a 5-stage pipeline over 100% of the 226 failed builds (not a sample): extract failing logs → group into error fingerprints → classify flaky-vs-broken → adversarial refute (a second agent argued the opposite verdict) → synthesize. 9 verdicts were overturned during the refute pass, which is the safeguard working.

Classification signals

  • red→green Same commit failed then passed with no change — the strongest flaky signal.
  • breadth Same failure across many unrelated branches that don't touch that code.
  • source smell A concrete non-determinism vector in the code: unfrozen clock, unordered first(), shared cache, random data, query-log accumulation, per-worker timer bleed.

Honesty notes

  • Two parsing bugs were caught and fixed mid-audit (a macOS tab-matching quirk that was silently dropping failures, and a missing fail/pass signal). The numbers here are from the corrected, re-run pass; earlier runs were discarded.
  • Pest's verbose mode truncates some long test class names; those are pinned by stack-frame file/line where possible and held at probable confidence otherwise.
  • Branch-diff correlation is heuristic (commit messages, stat, targeted diffs) — not a full per-file diff of every branch.
  • This is a read-only audit: no tests were edited, no PRs opened, no tickets filed. Output is this report and the underlying data.
