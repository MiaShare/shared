⭐ Headline: the merged PR over-claims what it delivered

  • “FormElementType::forContext() returns universals for LEAD_FORM”

None of the three exist in the merged tree. FormContext has only LEAD_CAPTURE/FORM/APPLICATION (FormContext.php:25-27); FormElementType has no forContext(); ContactDetailSource has no LEAD_FORM. The PR’s “PRD-alignment follow-ups” narrative landed only partially in the squash: other items it describes — the FormSubmitted marker interface (FormSubmitted.php:27) and the Form::pages typed cast (Form.php:59) — are in the tree, but these three LEAD_FORM / forContext() deliverables are not. The log reads “PRD-complete” while the code is not — which made the original “Done” defensible and is a likely reopen cause. Treat the commit message as unreliable; the sections below judge against the code.

What works (solidly shipped)

  • Class moves are clean. Old FormElementType (both Lead Capture + Enrollment), FormPageData/FormFieldData/ConditionData, FormPageTransformer all deleted and re-homed under app/Domains/FormBuilder/. Imported tree-wide by ≈116 files (~109 outside the domain’s own 7 — exact count varies with grep scope). No leftover dup/stub — only an intentional STATIC_AGREEMENT() queue-drain alias (FormElementType.php:65).
  • PRD 3 (storage) is the strongest. forms.pages migration (…add_pages_to_forms_table.php:24); BackfillFormPages action + forms:backfill-pages command genuinely idempotent (fingerprint match→skip, divergent→FAILURE unless --force-overwrite; BackfillFormPages.php:47-65,285-304), tested (BackfillFormPagesCommandTest.php). elements accessor synthesizes from pages both directions (Form.php:87-154); elementsByPage() reads pages with raw fallback (Form.php:310-337); elements column correctly deferred, not dropped.
  • PRD 5 decoupling works functionally. FormSubmitted marker interface (FormSubmitted.php:27); all 5 listeners type-hint it and resolve via getFormSubmissionId() (SendNewLeadNotification, ScheduleLeadCaptureSummary, CreateInboxConversationForLeadCapture, LeadCaptureFormSubmittedWebhook, AdvanceAutoTransitionsOnLeadCaptureFormSubmitted). Laravel walks class_implements() so all fire. Idempotency hardened with an org-scoped fast-path return (ProcessFormSubmission.php:69-84).
  • PRD 1 extraction skeleton. FormPagesSchema.php + FormPagesSchemaConfig.php are a composable, per-request schema builder; config controls excluded field types, page validators, owning-model / org / storage-prefix resolvers. ApplicationFormResource + ApplicationFormTemplateResource compose pagesSection() and layer their own sections.
  • Two live form runtimes share the extracted traits — as intended. The two parent components — the AI iframe path (…Ai/DynamicForm:34-35) and the non-AI iframe path (Livewire/LeadCapture/DynamicForm:36-37) — both use RendersFormFields / HandlesFormSubmission. (Their DynamicFormPage sub-components compose Filament InteractsWithForms separately and do not consume the traits.) This is the dedup the extraction was for, not dead code.
  • architecture.md updated to register + describe the domain.

  • FormPagesSchema cannot instantiate without Enrollment — imports App\Enums\Enrollment\ApplicationFormType (referenced 15×) + SensitiveFieldPattern (FormPagesSchema.php:11-12); docblock (:44-46) calls neutralization “intentionally deferred.”
  • FormBuilder/Enums/FormElementType.php:7 imports ApplicationFormType (legitimate use at :132, not dangling).
  • ProcessFormSubmission imports LeadCapture actions (:12-13) and hardcodes AutomationEvent::LeadCaptureFormSubmitted (“hardcoded for now”, :164). Correct for today’s only consumer; blocks a second form type until parameterized.
  • HandlesFormSubmission.php:9-10 imports LeadCapture CreateFormSubmission/UpdateFormSubmission.
  • → PRD 1 Req 1 and the “no LeadCapture imports” success criteria remain unmet.

🟠 PRD-spec items missing or deferred

  • FormContext missing LEAD_FORM — only LEAD_CAPTURE/FORM/APPLICATION (FormContext.php:25-27). PRD 2 spec’d {LEAD_CAPTURE, LEAD_FORM, FORM}; PRD 6 the superset. Impl = PRD 6’s set minus LEAD_FORM. Any FormContext::LEAD_FORM ref is a fatal Error.
  • Enum categorization API absent — no isUniversalType(), isEnrollmentType(), forContext() (PRD 2 Req 2). Categorization lives on ApplicationFormType instead; both PRD 2 success criteria unsatisfiable. (Commit body claims forContext() shipped; it did not.)
  • PRD 2 Req 7 — FormPagesSchema never references FormContext; the dropdown filters by ApplicationFormType + excludedFieldTypes. Intent met via a different mechanism.
  • PRD 4 shared rendering layer not built — resources/views/livewire/form-builder/fields/ does not exist. RendersFormFields does paging + resolution only — no field render, no validation-by-type. The per-type render match still lives un-extracted at …Ai/DynamicFormPage.php:106-312 (and its non-AI twin). PRD 4 success criterion 2 not met. Reasoned deferral (Filament PHP-DSL, not Blade-per-type), so 🟡 not 🔴. (Runtime hide_conditions lives in Enrollment/Form.php, not DynamicFormPage.)
  • PRD 5 Req 3 — no LEAD_FORM on ContactDetailSource; pipeline reuses LEAD_CAPTURE_FORM. Correct for the only live consumer; named case deferred with the Lead Form product.
  • PRD 5 Req 4 — event not renamed; FormSubmitted built as a marker interface (matches architecture.md; contradicts the PRD’s “rename” wording). Functionally fine.
  • PRD 6 Req 2 — form_context is a read-only VIRTUAL generated column derived from type, not a writable nullable string. Deliberate tradeoff (no drift from type; INPLACE/LOCK=NONE ALTER), but the enum cast is effectively read-only.

🟡 Hygiene / debt

  • PRD 6 slice is currently unconsumed. Widget::scopeFormContext() has zero callers anywhere, and FormContext is referenced only inside app/Widget.php. Migration + virtual column + index + cast + scope + enum form a vertical slice nothing reads. The migration docblock also promises a post-deploy NULL-row audit (:22-23) that does not exist — a second instance of the same narrative-vs-tree drift.
  • Test coverage gaps on core extracted surfaces: ProcessFormSubmission, FormPagesSchema, FormPageTransformer, and the whole PRD 6 FormContext slice have no dedicated tests. ProcessFormSubmissionException untested. The “all 5 listeners fire via the interface” claim has no regression test (listener tests call handle() directly).
  • ProcessFormSubmission re-invokes UpdateFormSubmission a second time purely to dispatch automation (afterCommit, :163-170). The second call writes no row (update gated on a non-empty field set; automationEvents excluded — UpdateFormSubmission.php:79-97) — it does an extra firstOrFail() SELECT + dispatches a job. The afterCommit defer is intentional + documented, but best-effort: if it throws, contact link + opt-prefs are committed while the automation event never fires.
  • PRD 3 Req 5 (partial) — LeadCaptureWidgetPagesTrait still emits the flat ['elements' => …] shape and the Edit page reads $form->elements; conversion is delegated to the model accessor + actions. Intent met, literal requirement not.
  • PR #6740 (open, CONFLICTING) — branched against the old Enrollment namespace; its migration + EMAIL/PHONE types already shipped in #6887. Stale; needs a full rebase onto FormBuilder or close.
  • Cosmetic — docblock at FormElementType.php:16-17 claims a “superset of” two paths that both point at the new namespace (should be the old LeadCapture + Enrollment FQCNs).

Bottom line

The mechanical extraction (PRD 1 moves + PRD 3 storage) is real and solid. The platform-neutrality promise (PRDs 1, 2, 4, 5) is intentionally half-done — FormBuilder still leans on Enrollment + LeadCapture, the FormContext/forContext() API the PRD specified doesn’t exist, and LEAD_FORM was deferred across three enums. The biggest risk is narrative drift: the PR’s commit message asserts PRD work (LEAD_FORM, forContext(), ContactDetailSource) that never reached the tree, so “Done” looked defensible while the code wasn’t. Fix the broken enrollment-shard import first (one line), then decide explicitly whether full neutrality + LEAD_FORM are PLAT-7 scope or a tracked follow-up — and correct the commit/ticket record so the gap is visible.
