Handwritten lead-card OCR ingestion

An end-to-end walkthrough of the new lead-card upload pipeline in PR #7032. A school admin uploads photos / scans / PDFs of inquiry cards; the app persists each file, then background jobs detect card bounding boxes, crop one image per card, OCR each card with OpenAI vision, and create or match a Contact. An Upload History widget reports per-file outcomes. Captured in the real running app driving the real model — 9 golden paths and 6 anti-paths, every backend outcome verified against the database.

How the feature works (read this first)

The upload page lives at /portal/lead-card-upload and is gated by the ocr-lead-upload feature. A school admin drops one or more inquiry-card images (JPG / PNG / WEBP) or a PDF and clicks Upload. The request persists the file(s) and rasterises any PDF pages synchronously, then queues background jobs:

1
PersistEach uploaded file (or PDF page) is rastered to S3 as a lead_image; the Upload History records a per-file outcome.
2
Detect & cropProcessLeadImage asks the model for card bounding boxes and creates one lead_card per detected card (whole-frame fallback if none found).
3
OCRProcessLeadCard sends the cropped card to OpenAI vision and stores the extracted fields in ocr_payload.
4
ContactIf a valid email or phone was read, the card is linked to a created-or-matched Contact; email/phone are tagged source Lead Card.

Each screenshot below pairs the browser Interaction with what it is Showing and the matching DB check. The queue connection is database, so jobs were drained with queue:work --queue=communications --stop-when-empty after every upload. Tip: click any screenshot to view it full-size.

⚠ Finding · should-fix

The lead_cards.outcome = 'created' value is unreachable

The pipeline works end-to-end, but every successful card — including ones that create a brand-new contact — is recorded as outcome = 'matched', never 'created'. Across this run, 9 distinct contacts were created from lead cards, yet 0 cards were labelled created (11 matched + 1 no_contact_details).

Root cause. ProcessLeadCard::resolveContact() sets the outcome from $contact->wasRecentlyCreated. But ContactService::firstOrCreateContactByEmailOrPhone() creates the contact via the CreateContact action (which returns an id) and then re-queries it with Contact::where(...)->firstOrFail(). A query-hydrated model has wasRecentlyCreated = false, so the "created" branch can never be taken.

Impact. The dedup logic itself is correct (no duplicate contacts are created), but operators reading the lead_cards audit cannot distinguish a card that created a new lead from one that matched an existing contact. Proven empirically below in G3 (a brand-new contact, created at the exact job-completion instant, still reported matched).
